# Модель безопасности

Агент с доступом к shell, файлам и управлению ПК — это потенциально очень опасная программа. Безопасность — не фича, а фундамент: её нельзя «добавить потом».

## Угрозы

1. **Ошибка модели** — агент удаляет не те файлы, делает `git push --force`, закрывает несохранённый документ.
2. **Prompt injection** — вредные инструкции в веб-странице, файле, ответе MCP-сервера, тексте на экране.
3. **Вредоносный агент или MCP-сервер из каталога.**
4. **Утечка секретов** — ключи в логах, в контексте модели, в отправке на сторонний сервер.

## Уровни риска инструментов

| Уровень | Примеры | По умолчанию |
|---|---|---|
| `read` | Read, Glob, Grep, список окон, скриншот | разрешено в пределах проекта |
| `write` | Write, Edit | спросить (или авто-разрешение в режиме «принимать правки») |
| `exec` | shell, запуск приложений, MCP-инструменты | спросить |
| `system` | мышь/клавиатура, UI Automation, завершение процессов, вне папки проекта | спросить, всегда показывать |
| `network` | WebFetch, WebSearch, загрузка файлов | спросить; «всегда» запоминает домен (для поиска — поисковик) |

## Правила разрешений

Как в Claude Code — списки `allow` / `ask` / `deny` с шаблонами, на уровне пользователя и проекта. `deny` всегда сильнее `allow`.

```toml
[permissions]
allow = ["Read", "Bash(git status)", "Bash(npm test:*)"]
ask   = ["Bash(git push:*)"]
deny  = ["Read(**/.env)", "Bash(rm -rf:*)", "PC(app:Banking*)"]
```

Режимы сессии: **По умолчанию** · **Принимать правки** · **Plan (только чтение)** · **Без подтверждений** (`bypass`, см. ниже) · **Автономный** (`bypass` плюс песочница для команд, см. «Песочница»).

### Режим `bypass`

Ничего не спрашивает: Shell, MCP, сеть и запись вне проекта идут сразу, в том числе `Read(.env)`. Включается в настройках («Режим для новых сессий») или `[permissions] mode = "bypass"` в пользовательском config.toml, `--mode bypass` в CLI. Решение пользователя и на его риск.

- Правила `deny` продолжают действовать.
- Проектный `.kairo/config.toml` включить его не может: репозиторий не должен отключать подтверждения.
- В интерфейсе режим подписан красным «Без подтверждений (опасно)». Shift+Tab переключает на него, только если он выбран в настройках.
- Откатить можно только правки `Write`/`Edit`. Shell, MCP и сетевые запросы — нет, а текст из файлов, веб-страниц и ответов MCP может содержать инъекции. Для долгих автономных задач нужна песочница (M3).

## Защита от prompt injection

- Всё, что пришло из инструментов, помечается как **данные**, не инструкции — и в промпте, и в UI.
- Результаты web/MCP/экрана не могут поднять уровень доверия сессии.
- Опасные действия после чтения недоверенного контента требуют подтверждения даже при правиле `allow` (taint tracking — P1).

## Мост UI ↔ ядро

Интерфейс — веб-страница в WebView2, и он рендерит текст от модели. Значит, интерфейс считаем **потенциально скомпрометированным** и не даём ему полномочий.

- Мост — только JSON-RPC через `PostWebMessageAsJson` / `WebMessageReceived`. `AddHostObjectToScript` не используется.
- Методы — намерения пользователя, а не команды. Методов вида «выполни команду» или «запиши файл» в протоколе нет. Ответ на запрос разрешения ядро принимает только для реально ожидающего запроса.
- Белый список методов, проверка origin (`https://app.kairo.local`) у каждого сообщения.
- Markdown от модели проходит через санитайзер, сырой HTML запрещён, CSP `script-src 'self'`. Mermaid и SVG — в sandbox-iframe.
- Навигация за пределы приложения и открытие новых окон блокируются. Ссылки открываются во внешнем браузере после подтверждения.

Даже при XSS в интерфейсе атакующий может максимум нажать «разрешить» на уже показанный запрос — и то это видно пользователю. Для `system`-действий подтверждение дополнительно идёт через нативный диалог оболочки (P1).

## Рой агентов (реализовано в CLI: `kairo swarm`)

Что сделано из спецификации ниже (топология `orchestrator`):

- **Интерфейс не командует роем.** Он присылает цель, папку и лимиты (`swarm.start`), просит паузу или продолжение (`swarm.stop`, `swarm.resume`) и отвечает на вопросы (`permission.respond`). Папка должна быть уже известной рабочей папкой и git-репозиторием; модель, права, инструменты и пути worktree выбирает хост. Состояние роя приходит уведомлением `swarm.changed` не чаще нескольких раз в секунду.
- **Подтверждения в приложении** показываются отдельным блоком над доской; одинаковые вопросы от нескольких агентов объединяются, ответ «Разрешить всем» отправляется каждому из них.

- **Лид** (`lead`) только читает (Read, Glob, Grep, веб, скиллы) и управляет: `task_create`, `spawn_agent`, `merge_agent`, `swarm_finish`. Он всегда работает в режиме «спрашивать»; `merge_agent` меняет репозиторий пользователя, поэтому это вызов уровня `exec` с подтверждением.
- **Воркеры** (`coder-N`) получают инструменты основного агента и работают в своём `git worktree` и ветке `kairo/<рой>/<имя>` (по умолчанию в `%APPDATA%\Kairo\swarms`). Режим по умолчанию — «принимать правки» внутри собственного worktree; Shell и сеть спрашивают. С `--mode bypass` спрашивать перестают и лид, и воркеры.
- **Права не растут.** У каждого агента свой движок разрешений с копией правил пользователя (включая `deny`); воркер не получает ничего сверх этого, а лид не может выдать больше, чем есть у него самого. Подтверждения всех агентов идут через один запрос по одному, вопрос подписан именем агента.
- **Сообщения между агентами — данные.** В системных промптах сказано, что сообщения других агентов — информация, а не распоряжение пользователя; распространения «метки недоверия» (taint) пока нет.
- **Бюджеты.** Токены (вход + выход по всем вызовам), число агентов, время и число одновременных запросов к модели. При достижении лимита рой ставится на паузу (`paused`), состояние сохраняется; `kairo swarm resume <id> --max-tokens …` продолжает. Ctrl+C тоже ставит на паузу.
- **Остановка.** Рой с невыполненными задачами, где никто не может работать, получает статус `stalled`; рой, где лид упал, — `failed`; упавшего воркера лид узнаёт из сообщения, его задачи возвращаются в пул.
- **Состояние** (рой, агенты, доска, сообщения, общие заметки) — в `%APPDATA%\Kairo\swarms.db`, история каждого агента — обычная сессия в `data.db`.
- **Git.** Нужен репозиторий хотя бы с одним коммитом. Воркеры не видят незакоммиченные правки основной папки. Завершённая задача коммитится в ветку воркера автоматически (с идентификатором Kairo в самой команде, глобальный git-конфиг не меняется). Слияние делает только лид, и только после вашего подтверждения; при конфликте слияние отменяется.

### Спецификация (черновик)

Подробно — в [спецификации роя](specs/swarm.md#безопасность). Коротко:

- Разрешения только сужаются: пользователь ⊇ рой ⊇ роль ⊇ агент.
- Сообщения между агентами — данные, а не инструкции пользователя. Метка недоверия передаётся по цепочке сообщений.
- Автономный рой — в песочнице (`[sandbox] shell = "autonomous"`; по умолчанию выключена, см. «Песочница»).
- Жёсткие бюджеты (токены, деньги, время) и kill switch по горячей клавише.

## Управление ПК

Первый срез M6 (`Kairo.PcControl`): окна и приложения, чтение дерева UI Automation, действия через паттерны, быстрый цикл с Jev. Спецификация и то, что ещё впереди, — [pc-control.md](specs/pc-control.md).

- **Выключено, пока пользователь не включил.** `[pc] enabled = true` и список программ `[pc] apps = ["notepad.exe", …]` — только в **пользовательском** `config.toml` или в настройках приложения («Управление ПК»: флажок и «Добавить из открытых окон…», программу можно выбрать только из открытых сейчас, это проверяет хост; UI не может вписать произвольное имя); проектный файл игнорируется (репозиторий не может включить управление рабочим столом или расширить список). Без списка инструментов нет вовсе.
- **Только программы из списка.** Окно любой другой программы не читается и не трогается; в списке окон (`PcWindows`) они не показываются.
- **Никогда, даже если в списке:** терминалы (`cmd`, `powershell`, `pwsh`, Windows Terminal, `bash`, `wsl`), менеджеры паролей (KeePass, 1Password, Bitwarden и др.), системные инструменты (`regedit`, `mmc`, `taskmgr`, окна UAC и входа), IDE со встроенным терминалом и сам Kairo. Управление терминалом обошло бы правила и песочницу инструмента `Shell`.
- **Всегда спрашивает.** Все инструменты управления (`PcObserve`, `PcAct`, `PcLaunch`, `PcPursue`) имеют уровень риска `System`. Режим `bypass` на них **не действует**: спрашивают и в нём. Правило `allow = ["PcAct(notepad.exe)"]` снимает вопрос для одной программы и одного инструмента. В режиме `plan` они запрещены; `PcWindows` читает только список разрешённых окон и без вопросов.
- **Быстрая модель не решает опасное.** Шаги вроде «удалить», «отправить», «оплатить», «выйти», «закрыть», «не сохранять» (по-английски и по-русски), поля паролей и опасные сочетания клавиш (`alt+f4`, `ctrl+w`, всё с Windows-клавишей) модель решений не выполняет ни при какой уверенности: цикл останавливается и возвращает экран большой модели и пользователю. Список таких шагов составляет ядро, а не модель.
- **Только из списка вариантов.** Быстрая модель выбирает из действий, которые реально есть в дереве: кнопка, которую можно нажать, поле, куда можно ввести, подготовленный текст или сочетание из плана. Придумать действие или текст она не может; ответ вне списка отвергается.
- **Пароли.** В поле пароля (`IsPassword`) Kairo не вводит текст, и его содержимое не читается ни в состояние для модели, ни в журнал.
- **Стоп.** Клавиша **Pause** останавливает цикл и отдельные действия в любой момент (проверяется перед каждым шагом и ещё раз перед действием). Отмена хода агента делает то же.
- **Границы цикла.** Лимит шагов (25 по умолчанию, не больше 60), порог уверенности (0,7), остановка при неизменном экране три шага подряд, при двух шагах «без эффекта» подряд и при недоступной быстрой модели (тогда продолжает большая).
- **Политики.** `PcRunPolicy` принимает политику-данные (шаги, тексты, рефлексы, лимиты); ядро проверяет её, показывает пользователю целиком (программа, каждый шаг и рефлекс, лимиты) и спрашивает даже в режиме `bypass`. Политика привязана к одной программе из списка; рефлексы — единственное место, где рискованный клик можно одобрить заранее, и пользователь видит его в этом окне.
- **Устаревшие id.** Действие называет номер просмотра экрана; id из старого просмотра отклоняется, поэтому нельзя попасть в не тот элемент после изменения окна.
- **Что уходит в облако.** Дерево окна (имена и состояния элементов, без паролей) отправляется в Jev (api.typesafe.ai) на каждом шаге, а большой модели — в ответах инструментов. Не включайте программу в список, если её содержимое нельзя отправлять провайдерам.
- **Что не закрыто.**
  - Нет скриншотов и клика по координатам: приложения без дерева UI Automation (игры, часть Electron) недоступны; цикл прямо говорит об этом.
  - Индикатор «Kairo управляет ПК · Pause — стоп» горит в строке состояния окна Kairo, пока работает инструмент управления; поверх чужих окон его нет (отдельный экранный индикатор — впереди), так что при работе в другой программе опирайтесь на клавишу Pause и подтверждения.
  - Клик мышью по центру элемента из дерева используется для пунктов классического меню Win32 (паттерны там не срабатывают); он двигает курсор пользователя.
  - Программа получает фокус при каждом действии; в это время ввод пользователя может попасть в неё.
  - Подтверждение для `PcPursue` запрашивается один раз на подцель, а не на каждый шаг: шаги внутри подцели идут без вопросов, кроме опасных.

## Песочница

Реализована для инструмента `Shell` в Windows (`AppContainerSandbox`, `Kairo.Windows`). Включается в **пользовательском** `config.toml`; проектный конфиг не может её выключить или расширить (значения `[sandbox]` из `.kairo/config.toml` игнорируются).

```toml
[sandbox]
shell = "autonomous"        # off (по умолчанию) | autonomous | always
network = false             # исходящая сеть для команд
read = ["C:/Users/me/AppData/Local/Programs/Python/Python312"]   # что ещё разрешено читать
memory_mb = 4096            # память на всё, что запустила одна команда
```

- `autonomous` — команды в режиме `bypass` и команды воркеров роя идут через песочницу; `always` — все команды всех сессий; `off` — как раньше.
- **Что делает песочница.** Команда запускается в AppContainer — процесс с урезанным токеном. Он пишет и читает только папки, которые ему выдали: рабочую папку сессии (у воркера — его worktree) и свой домашний каталог `%LOCALAPPDATA%\Kairo\sandbox\home`. Windows и Program Files читаются (иначе не запустятся PowerShell и .NET SDK); профиль пользователя, остальные диски и документы закрыты. Сеть выключена целиком, включая loopback. Процесс живёт в Job Object: лимит памяти, при отмене, таймауте и закрытии приложения убивается всё дерево.
- **Доступ выдаётся через ACL** (`icacls`, запись для SID контейнера на папку проекта). Приложение снимает её при закрытии; если оно завершилось аварийно, запись остаётся, но без контейнера она никому ничего не даёт. Убрать вручную: `icacls <папка> /remove *<SID>` (SID — `AppContainerSandbox.ContainerSid`).
- **Файловые инструменты в той же клетке.** При включённой песочнице `Write` и `Edit` отказываются менять файлы вне тех же папок.
- **Отказ вместо обхода.** Если песочница нужна, но её не удалось создать (старая Windows, `icacls` не отработал, хост без неё), команда **не выполняется** с понятной причиной; она не уходит в обычный запуск.
- **Что не закрыто.**
  - `Read`, `Grep`, `Glob`, `WebFetch`, `WebSearch` и MCP работают как обычно, вне песочницы. В `bypass` модель всё ещё может прочитать `~/.ssh` и отправить это через `WebFetch`.
  - `git` в песочнице не запускается: Git for Windows открывает устройство `NUL`, а AppContainer на обычной Windows 10 его не получает. Модели в результате команды так и сказано. Запускать git «снаружи» нельзя: хуки, `fsmonitor` и алиасы из чужого репозитория выполняют код. Воркерам git не нужен: коммиты делает рой.
  - Инструменты из профиля пользователя (Python, Node, ставившиеся «для себя») не видны: их папку надо добавить в `read`. `dotnet` из Program Files работает сразу; `python` и `pytest` проверены с выданной папкой Python.
- **Запасные варианты** (Windows Sandbox, WSL) — не делались: ради `git` и сети нужна более тяжёлая изоляция, это отдельное решение.

## Чекпоинты

Каждая запись файла инструментами `Write` и `Edit` идёт после снимка: перед первым изменением файла в запросе сохраняется его прежнее содержимое (или факт, что файла не было). Под каждым запросом, который что-то менял, есть кнопка «Откатить…»: в диалоге видно каждый файл, что с ним будет и разницу, и можно выбрать, какие файлы откатывать. Это главная страховка от ошибок модели.

- **Что не покрыто.** Действия команд (`Shell`), MCP-инструментов и всё, что агент сделал вне `Write`/`Edit`, не откатывается. Это сказано в самом диалоге.
- **Чужие изменения не затираются молча.** Если файл изменили после агента (вы сами или команда), он помечается «Файл изменили после агента» и по умолчанию не выбран; перезапись возможна только явным выбором.
- **Интерфейс выбирает только из записанного.** Путь, которого нет в чекпоинте, игнорируется: откат не может записать или удалить произвольный файл.
- **Откат запрещён, пока агент работает** в этой сессии. После отката модель получает пометку и должна заново прочитать файлы перед правкой.
- Файлы больше 2 МБ не сохраняются; откат такого файла помечается недоступным.

## Режим планирования

В режиме `plan` агент только читает. Закончив, он вызывает `ExitPlanMode` с планом, и интерфейс показывает план целиком с тремя вариантами: выполнять с автоприёмом правок, выполнять с подтверждением каждой правки или вернуться к планированию.

- Этот вызов **всегда спрашивает** в режиме `plan` и никакое правило `allow` его не пропускает; вне режима `plan` он запрещён.
- «Не спрашивать» для плана означает «принимать правки», а не «больше не спрашивать про планы»: такое правило не запоминается.
- Режим меняет цикл агента по ответу пользователя, а не модель и не интерфейс по собственному решению.

## Скиллы, свои команды и память

- **Скиллы** — папки `SKILL.md` (формат Claude Code) в `%APPDATA%\Kairo\skills` и `<проект>\.kairo\skills`. В системный промпт попадают только имена и описания; тело модель загружает инструментом `Skill` (риск `read`, без подтверждения) или пользователь запускает командой `/имя`. Скилл проекта — текст из репозитория, как `AGENTS.md`: он приходит как данные, и действия по нему всё равно проходят проверку прав.
- **Свои команды** — `<имя>.md` в `commands` (пользовательская папка или `.kairo` проекта) с `$ARGUMENTS`. Команда запускается только набором `/имя` пользователем; её текст уходит модели скрытой заметкой, в ленте виден набранный текст.
- **Встроенные** — `/help`, `/compact [что сохранить]`, `/remember [текст]`. Они выполняются в хосте, а не моделью.
- **Память** — `%APPDATA%\Kairo\memory.md`, попадает в системный промпт всех сессий. **Пишет в неё только пользователь** (`/remember`, одна строка до 500 символов): у агента нет инструмента записи, поэтому страница или репозиторий не могут оставить в памяти постоянную инструкцию. Файл можно править и руками.

## Хуки

Хук — команда PowerShell из `[[hooks]]` в config.toml, которая запускается на событии: `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`. Она получает событие как JSON на stdin (имя события, папка, инструмент и его ввод, ответ инструмента, текст запроса). Код выхода 2 блокирует: вызов инструмента (`PreToolUse`), запрос (`UserPromptSubmit`); для `PostToolUse` и `Stop` текст из stderr уходит модели (при `Stop` агент продолжает работу, не больше двух раз за запрос). Текст из stdout при коде 0 у `UserPromptSubmit` попадает к модели скрытой заметкой.

- **Только из пользовательского файла.** Хук — это произвольная команда на машине пользователя. Проектный `.kairo/config.toml` хуки не добавляет и не меняет (как и `mcp.json`, обновления и бэкенд поиска).
- **Хук только ужесточает.** `PreToolUse` выполняется до проверки прав, и ответ «не блокировать» ничего не разрешает: правила, режим и подтверждения работают как раньше.
- **Сбой хука не блокирует.** Таймаут (30 с по умолчанию), ошибка запуска или любой другой код выхода пропускают вызов дальше. Если хук — это защита, пишите его так, чтобы он блокировал явным кодом 2, и помните, что его падение защиты не даёт.
- **Сабагенты.** Хуки `PreToolUse` и `PostToolUse` действуют и на вызовы сабагента; `UserPromptSubmit` и `Stop` — только на основного агента.
- Хуки не получают секретов, кроме того, что есть в окружении самого приложения и в тексте события (ввод инструмента может содержать то, что агент прочитал).

## Сабагенты

`Task` запускает отдельный цикл агента со своим контекстом и возвращает один итоговый отчёт. Сам вызов `Task` — риск `read` и подтверждения не просит. Вся защита в том, что сабагент не получает прав сверх родителя:

- Он использует **тот же движок разрешений и тот же запрос подтверждения**. Его `Write`, `Shell` и сетевые вызовы показываются пользователю, как у основного агента; `deny`-правила, режим `plan` и `bypass` действуют и на него. «Всегда разрешать» на его вызове запоминается как для основного.
- Набор инструментов уже: `explore` — только Read, Glob, Grep, WebFetch, WebSearch (записать он не может физически); `general` — всё, кроме `Task`, `TodoWrite` и `ExitPlanMode`. Сабагент не запускает сабагентов и не выходит из режима плана.
- Он ничего не помнит о разговоре: родитель сам пишет ему задание. Родитель видит только отчёт, а отчёт — это результат инструмента, то есть данные, а не инструкции (см. «Защита от prompt injection»).
- Лимит — 40 вызовов модели. Правки файлов сабагента записываются в чекпоинт того же запроса и откатываются вместе с остальными.

## Веб-инструменты

`WebFetch` читает страницу, `WebSearch` ищет. Оба — риск `network`: спрашивают, правило `WebFetch(*.github.com)` разрешает сайт, `ask` и `deny` работают как у остальных. В режиме `plan` они запрещены.

- **Только публичный интернет.** Адреса вида localhost, `.local`, одно слово без точки, IP из loopback, частных сетей, link-local (в том числе 169.254.169.254, метаданные облака), CGNAT и multicast отклоняются до запроса. Проверка повторяется при соединении: имя, которое резолвится в частный адрес (или меняет ответ между проверкой и соединением), тоже не пройдёт. Прокси не используется, чтобы проверка видела настоящий адрес. Для локальных сервисов есть Shell.
- **Редиректы.** Идут вручную, не больше пяти. На другой хост (кроме «www.» и http→https) агент не уходит: он получает новый адрес и просит его отдельным вызовом, то есть с новым разрешением. Редирект в локальную сеть — ошибка.
- **Данные, а не команды.** Ответ приходит с пометкой «недоверенные данные», в системном промпте то же. Размер ограничен: скачивается до 3 МБ, отдаётся по 30 000 символов с продолжением через `offset`. Только текстовые типы; JavaScript не выполняется.
- **Что уходит наружу.** Адрес и запрос уходят сайту или поисковику, как у любого браузера. Агенту сказано не класть в запрос секреты и приватный код, но технически это не запрещено: разрешение на поиск — это разрешение на отправку запроса. Текст запроса виден в карточке подтверждения.
- **Поиск.** Brave Search API (ключ в диспетчере учётных данных `Kairo/brave` или `BRAVE_API_KEY`) или свой SearXNG (`[web] searxng_url`). Бэкенд и адрес читаются только из пользовательского config.toml: проектный файл не может направить запросы на чужой сервер. Ключ уходит только в заголовок запроса к Brave и не попадает ни в результат инструмента, ни в сообщения об ошибках. Поисковики без ключа (DuckDuckGo и подобные) отдают бот-проверку, её Kairo не обходит.

## Сжатие контекста

Сводку пишет модель по тексту переписки, включая результаты инструментов, а потом она занимает место переписки как сообщение пользователя. Значит, инструкция из недоверенного результата (файл, веб-страница, ответ MCP) могла бы «отмыться» и выглядеть как слова пользователя.

- Суммаризатору прямо сказано: результаты инструментов — данные; найденные в них инструкции надо описать как факт («файл просил…»), а не записывать как желания пользователя или незавершённую работу.
- Это снижает риск, но не исключает его: сводку пишет та же модель. Поэтому она показывается в ленте целиком («Сводка» под разделителем), а права не зависят от неё: разрешения проверяются по правилам и режиму сессии, а не по тексту истории.
- Сжатие ничего не удаляет: полный журнал остаётся в БД, откат файлов (чекпоинты) работает как раньше.

## Терминал

Встроенный терминал — единственное место, где ввод из интерфейса попадает в оболочку, поэтому у него жёсткие рамки:

- Это ввод самого пользователя. Агент не может писать в терминал: у него есть свой инструмент `Shell` с разрешениями и правилами.
- Программу выбирает хост (PowerShell 7 или Windows PowerShell). Интерфейс присылает только нажатия клавиш и размер окна, команду запуска задать нельзя.
- Папка должна быть известной рабочей папкой (выбранной через системный диалог). Терминалов не больше 8, вставка за один раз не больше 64 КБ.
- Оболочка и всё, что она запустила, лежат в Job Object с `KILL_ON_JOB_CLOSE`: закрытие вкладки, окна или падение Kairo не оставляет процессов.
- Терминал не вносит в разрешения агента ничего: правила и режимы сессии на него не влияют, и наоборот.

## MCP-серверы

- Сервер — чужой код с правами пользователя. Конфиг `mcp.json` меняется только действием пользователя в интерфейсе или вручную; агент не может добавить сервер.
- Конфигурации из репозиториев (`.mcp.json`) не читаются, чтобы открытие проекта не запускало процессы.
- Все вызовы MCP-инструментов — риск `exec`: по умолчанию спрашиваем. Подсказки сервера (`readOnlyHint` и подобные) в расчёт не берутся. Разрешить сервер целиком можно правилом `mcp__server__*`.
- Ответы серверов — данные, а не инструкции (см. «Prompt injection» выше): они не меняют режим и разрешения сессии.

## Агенты и MCP из каталога

- Манифест явно декларирует нужные инструменты и разрешения — пользователь видит их перед установкой.
- Агент не может выдать себе разрешения сверх декларированных.
- Обновление, расширяющее разрешения, требует повторного подтверждения.
- Реестр модерируется через PR; закрепляем версии по хэшу коммита.

## Секреты

- Ключи — только в Windows Credential Manager.
- Маскирование известных секретов в логах и в контексте модели.
- Никакой телеметрии по умолчанию. Если появится — opt-in и без содержимого сессий.
