# Спецификация: политики решений (черновик v0)

## Принцип: «LLM компилирует — System 1 исполняет»

Большая модель не принимает каждое решение сама. Она один раз **описывает задачу как политику**: как видеть состояние, какие есть действия, какие вопросы задавать на каждом шаге и когда звать на помощь. Дальше политику в цикле исполняет быстрая модель решений (System 1, например Jev), а LLM подключается только при эскалации и для периодического пересмотра.

```
LLM (секунды, редко)  ──пишет──▶  политика (JSON)  ──исполняет──▶  System 1 (сотни мс, постоянно)
        ▲                                                                       │
        └────────────── эскалация, логи решений, пересмотр ◀────────────────────┘
```

Принцип общий для всего Kairo:
- **управление ПК** — план с кандидатами из дерева UI Automation ([pc-control](pc-control.md));
- **игры** — пример ниже;
- **повторяющиеся задачи** — разбор почты, сортировка файлов, массовые однотипные действия;
- **рой** — правила распределения задач между агентами (P2).

## Три уровня скорости

| Уровень | Кто решает | Время | Для чего |
|---|---|---|---|
| **Рефлексы** | детерминированные правила из политики, без модели | < 10 мс | срочное и очевидное: «HP < 25% → выпить зелье», «появилось окно ошибки → Esc» |
| **System 1** | модель решений по вопросам из политики | 70–500 мс | тактика: какое действие из доступных |
| **System 2** | LLM | секунды | стратегия: написать и переписать политику, разобрать непонятную ситуацию |

## Восприятие: System 1 слепой

Jev понимает только текст. В обычных программах текст даёт UI Automation, но в играх дерева UI нет, есть только пиксели. Поэтому политика обязательно описывает, **как превратить экран в текстовое состояние**. Это должно происходить быстро и локально, иначе весь выигрыш в скорости теряется.

Источники состояния, от лучшего к худшему:

1. **API игры, моды, лог-файлы, консоль** — точно и мгновенно. Пример: игры с поддержкой модов, RCON, эмуляторы с API.
2. **Локальное машинное зрение** — набор готовых экстракторов Kairo:
   - `ocr` — встроенный в Windows OCR (`Windows.Media.Ocr`), числа и текст в заданной области;
   - `bar` — заполненность полоски (HP, мана) по цвету пикселей;
   - `template` — какой сейчас экран (карта, бой, меню, награда) по шаблонам;
   - `pixel` — цвет в точке (индикаторы, кулдауны);
   - `detect` — детектор объектов (ONNX, YOLO-подобная модель; P2).
3. **VLM на каждом кадре** — не используем в цикле: слишком медленно. Только при эскалации.

LLM, составляя политику, сама размечает области экрана: делает скриншот и описывает, где HP, где рука карт, где кнопка «Конец хода».

## Формат политики

JSON, валидируется по схеме. **Политика — это данные, а не код.** Экстракторы, действия и выражения берутся только из фиксированной библиотеки Kairo, исполнить произвольный код через политику нельзя.

Пример — карточный рогалик:

```jsonc
{
  "$schema": "kairo.policy/v0",
  "goal": "Пройти первый акт",
  "target": { "window": "MyCardGame.exe" },           // ввод идёт только в это окно
  "tick": { "interval_ms": 250, "max_steps": 20000 },

  // 1. Восприятие: экран → поля состояния
  "observe": {
    "screen": { "type": "template", "templates": { "battle": "tpl/battle.png", "map": "tpl/map.png", "reward": "tpl/reward.png" } },
    "hp":     { "type": "bar", "region": [40, 20, 200, 12], "color": "#c0392b" },
    "energy": { "type": "ocr", "region": [90, 610, 40, 40], "format": "int" },
    "hand":   { "type": "ocr_list", "regions": "slots/hand.json" },
    "intent": { "type": "ocr", "region": [820, 180, 160, 30] }
  },

  // 2. Состояние в виде текста для System 1
  "state": "Экран: {screen}. HP: {hp}%. Энергия: {energy}. Карты в руке: {hand}. Враг собирается: {intent}.",

  // 3. Действия: что можно сделать и как это нажать
  "actions": {
    "play":     { "input": "click", "at": "slots/hand.json#{i}" },
    "end_turn": { "input": "key", "key": "E" },
    "pick_reward": { "input": "click", "at": "slots/reward.json#{i}" },
    "map_node": { "input": "click", "at": "slots/map.json#{i}" }
  },

  // 4. Рефлексы — без модели
  "reflexes": [
    { "when": "screen == 'battle' && energy == 0", "do": "end_turn" }
  ],

  // 5. Вопросы к System 1 — свои для каждого режима
  "modes": {
    "battle": {
      "choice": { "ask": "Какую карту сыграть или закончить ход?", "options": "hand → play[i]", "extra": ["end_turn", "stuck"] }
    },
    "reward": {
      "choice": { "ask": "Какую награду взять для колоды на атаку?", "options": "reward → pick_reward[i]", "extra": ["skip", "stuck"] }
    },
    "map": {
      "choice": { "ask": "Куда идти? Предпочитаем элиту, если HP > 60%", "options": "map → map_node[i]", "extra": ["stuck"] }
    }
  },

  // 6. Проверки прогресса
  "checks": [
    { "every_s": 30, "type": "score", "ask": "Насколько хорошо идёт забег?", "levels": ["провал", "плохо", "нормально", "хорошо"] },
    { "every_s": 10, "type": "yes",   "ask": "Забег окончен?" }
  ],

  // 7. Когда звать LLM
  "escalate": {
    "confidence_below": 0.6,
    "on": ["stuck", "unknown_screen", "no_state_change:20", "score:провал"],
    "review_every_s": 600
  }
}
```

## Цикл исполнения

1. Захват кадра (Windows.Graphics.Capture) или чтение API игры.
2. Экстракторы → поля состояния → текст по шаблону `state`.
3. Неизвестный экран (ни один шаблон не подошёл) → эскалация.
4. Проверка рефлексов: если сработал — действие сразу, без модели.
5. Вопрос System 1 для текущего режима → выбор + уверенность.
6. Ворота: уверенность ниже порога или выбран `stuck` → эскалация.
7. Ввод — только в целевое окно. Если окно потеряло фокус — пауза.
8. Запись в лог: состояние, вероятности, выбор, что изменилось.

## Обратная связь: политика учится

LLM периодически (`review_every_s`) и при каждой эскалации получает логи решений: где была низкая уверенность, где застревали, что приводило к провалу. После этого она **переписывает политику**: уточняет вопросы, добавляет рефлексы, перенастраивает экстракторы. Версии политик хранятся, чтобы можно было откатиться. Хорошие политики можно публиковать в каталоге (P2): «политика для игры X».

## Что подходит, а что нет

| Подходит | Плохо подходит |
|---|---|
| Пошаговые игры: карточные, стратегии, RPG-бои, головоломки | Реакционные игры: шутеры, файтинги, платформеры с точными таймингами |
| Меню, диалоги, инвентарь, крафт | Задачи, где состояние не извлечь в текст |
| Idle- и менеджмент-игры | Игры, где каждый экран уникален |
| Однотипные задачи на ПК | |

Для реакционных игр 70–500 мс System 1 плюс захват кадра — слишком медленно. Там можно опираться только на рефлексы, а это уже обычный скриптовый бот.

## Безопасность и правила

- Политика проходит валидацию по схеме, перед запуском пользователь видит: целевое окно, список действий, лимиты.
- Ввод — только в окно из `target`. Kill switch по глобальной горячей клавише, видимый индикатор «агент играет».
- Лимиты: шаги, время, деньги на модели.
- **Только одиночные игры и игры, правила которых разрешают автоматизацию.** Kairo не обходит античиты и не читает память защищённых процессов. Онлайн-игры с запретом ботов не поддерживаются: это нарушение их правил и риск бана аккаунта пользователя.

## Открытые вопросы

- Язык выражений для рефлексов: минимальный безопасный (сравнения, `&&`, `||`) или готовый (CEL, NCalc)?
- Стоит ли вынести формат в общий стандарт и совместить с `swarm.toml` и манифестом агента?
- Как LLM удобнее всего размечать области экрана: координаты, привязка к якорным шаблонам, относительные доли окна (устойчивее к смене разрешения)?
